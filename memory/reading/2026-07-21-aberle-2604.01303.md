## What are the polynomial functors used FOR?

Polynomial functors `p = (A,B)`, `P(y)=Σ_{a:A} y^{B(a)}`, are **program interfaces** — the
interface of a dependent function `(a:A)→B(a)` (positions = inputs, directions = outputs).
- **Implementations** = morphisms `p ⇒ Free q` (Def 2.1): given any input to `p`, produce a
  computation in the **free monad on `q`** that returns an output. A bare lens `p⇒q` = the
  special case "assumed interface called exactly once"; the free monad lifts this to zero/one/many
  calls. This is explicitly **assume-guarantee reasoning**.
- **Specifications** = **dependent polynomials** `(C,D)` over `p` (Def 5.1): `C:A→Set`
  preconditions, `D:(a:A)→C(a)→B(a)→Set` postconditions. This is literally a **Hoare triple**
  `{C(a)} f(a) {D(a,-,-)}`. Categorically a polynomial functor on the arrow category `Type^→`
  lying over `p` via `cod`.
- Sum `Σ_{u:U} P(u)` (= coproduct in **Poly**) handles multi-function modules; `p⇒Free zeroPoly`
  = a closed module = an ordinary dependent function.

## The abstract structure (§7) — this is the "closest prior art" part

NOT a single classification/equivalence. It is a **monoidal functor + lax monoidal presheaf +
monoidal natural transformation** package (Def 7.1 "compositional verification framework"):
- **Int** = category of interfaces: objects polynomials, morphisms `p⇒Free q` composed by
  **Kleisli composition of the free monad monad on Poly**.
- **Spec** = category of specifications: objects `(p,r)` (poly + dependent poly), morphisms
  = (implementation, verification) pairs.
- Forgetful `π: Spec→Int` is **strictly monoidal** w.r.t. `⊕` (sum of polynomials) — this is
  *why* verified implementations compose along wiring diagrams.
- `Mealy: Int^op→Set` is a **lax monoidal presheaf** (systems); `DepMealy: Spec^op→Set` likewise;
  projection `DepMealy ⇒ Mealy∘π` is a **monoidal natural transformation**.
- Appendix A: a **second** monoidal structure on Int, the *parallel/conjunctive sum* `p‖q`
  (`A∨C = A+C+A×C`), for **concurrent** modules that call either or both dependencies.

**No classification theorem, no equivalence, no Zappa-Szép product, no distributive law between
two monoids, no cohomology/obstruction anywhere.** The only "distributive law" in sight is the
monad structure itself (Kleisli), not an interacting pair of monoids.

## Free monads / Kleisli as implementations?

Yes — this is the spine of the paper. Implementations are Kleisli arrows `p⇒Free q`; `comp`/`compDep`
= Kleisli composition; Thm 3.1 (wiring diagrams compose to one implementation) and Thm 5.3
(verifications compose along the same wiring diagrams) are the compositionality results. Same
mechanism MacBeth calls "tactics = ◁-monoid / free-monad structure." Explicit link to Libkind-Spivak
"Pattern Runs on Matter" (free monad monad as module over cofree comonad comonad) for the Mealy layer.

## Agent orchestration / H² / two interacting systems?

- **Agents:** none. Composition is via Spivak's **operad of wiring diagrams** (boxes = modules,
  wires = dependencies). §9 flags automation/tactics and information-flow/security as *future work*.
- **H² / obstructions / cohomology:** **NONE.**
- **Two interacting systems:** only the *parallel sum* `p‖q` (Appendix A) — an unobstructed
  symmetric monoidal product for concurrency (call either/both). No shared-resource contention,
  no non-trivial interaction beyond the free choice `A∨C`. No welding of two monoids.
